# Lab 6, Part 2: Codebase bloat and redundancy audit

This records the pre-refactor audit. Implemented changes and validation are in
[Part 3](lab6-refactoring.md).

## Scope and method

Reviewed all 37 TypeScript/TSX files under `src/` and `client/src/`, including the
backend controllers/services/models and frontend components/hooks/API client.
Used source searches, TypeScript AST inspection, line counts, import-reference
searches, and comparison with `docs/openapi.yaml`. Tests and configuration were
read where needed to assess safe refactoring boundaries. Generated output and
historical lab logs were excluded from the source inventory.

This audit identifies maintenance issues; repetition alone does not establish
whether code was generated by AI. No application code was changed for Part 2.

## Findings and suggested order

| Order | Finding                                                        | Evidence                                                                                                                                                                | Suggested action                                                                                                                                     |
| ----- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | Unused, conflicting backend DTO module                         | `src/types/api.ts` duplicates four active DTO interfaces and two domain enums; no import/re-export references were found in repository source, tests, or configuration. | Confirm no external consumers, then remove the obsolete module and use `src/types/reservation.ts` as the backend DTO source.                         |
| 2     | Repeated controller error forwarding                           | Three reservation handlers and one resource handler repeat `catch (error: unknown) { next(error); }`.                                                                   | Use the existing Express 5 promise-error forwarding after verifying error-response regressions; retain centralized middleware and typed controllers. |
| 3     | Repeated frontend message fallback                             | Four hook catch paths select `Error.message` or an operation-specific fallback.                                                                                         | Consider a small typed message helper if refactoring these hooks; preserve the booking-specific conflict message and each operation's fallback.      |
| 4     | Repeated frontend identifier predicate                         | The same 24-hex-character pattern appears in API validation and booking validation.                                                                                     | Consider one frontend-only identifier helper, reused by both callers; retain backend validation independently.                                       |
| 5     | Matching frontend/backend wire contracts maintained separately | Four DTO shapes and two enum-value sets match across the active API type files.                                                                                         | Keep both aligned with the authored OpenAPI contract; consider contract checks before changing module boundaries.                                    |

These are refactoring candidates, not observed runtime failures. The first two
offer the clearest cleanup; the smaller frontend helpers should earn their extra
modules through actual reuse and simpler callers.

## Duplicate handlers and error logic

### Backend controllers

The four identical catch blocks are at:

- `src/controllers/reservation.controller.ts:19`, `:33`, and `:47`.
- `src/controllers/resource.controller.ts:15`.

They only forward errors; the request parsing, service calls, DTOs, and success
statuses differ and should remain in their respective controllers.

The installed runtime is Express **5.2.1**, with router **2.2.0**. A targeted read
of the router's `Layer.handleRequest` confirmed that it forwards returned-promise
rejections to `next`. These async handlers can therefore use that existing behavior
without introducing an async-handler package or wrapper. Keep
`src/middleware/error.middleware.ts` responsible for structured errors. Validate
invalid-input `400`, missing-entity `404`, conflict `409`, and sanitized `500`
responses before accepting such a refactor.

### Frontend

There is **one** browser `fetch` call, at `client/src/api/campushubApi.ts:72`, inside
the shared `request` function beginning at line 58. No Axios usage or HTTP/error-body
parsing was found in React components. JSON parsing, response validation, and
`ApiError` creation are already centralized.

Message selection is repeated at `client/src/hooks/useResources.ts:26`,
`client/src/hooks/useUserReservations.ts:50` and `:86`, and
`client/src/hooks/useBooking.ts:68`. A possible helper would accept `unknown` and
an explicit fallback and return a string. Booking must retain its special `409`
message before using the generic fallback.

The API client's nested catches distinguish network errors, unreadable bodies,
HTTP failures, caller cancellation, and timeouts. They are different responsibilities,
not four copies of one handler. Its `finally` also releases timers and listeners.
The hooks' abort and mounted guards prevent stale updates and must survive cleanup.

conservative check of the roughly 150-line threshold:

**No component module exceeds 150 lines.** There is no oversized component with

`client/src/api/campushubApi.ts` is 189 lines, but is not a React component. Its
runtime response guards could be extracted if they grow; splitting it solely to
meet a component threshold would add navigation without resolving state coupling.

## Redundant interfaces and contract drift

### Obsolete backend types: confirmed duplication and drift

Compare `src/types/api.ts` with the actively imported `src/types/reservation.ts`:

| Definition                 | Obsolete module                       | Active backend/OpenAPI contract                 |
| -------------------------- | ------------------------------------- | ----------------------------------------------- |
| `Resource`                 | `resourceType`, `available`           | `type`, `isAvailable`                           |
| `ErrorResponse`            | `error`, `message`                    | `code`, `message`                               |
| `Reservation`              | Same wire fields; enum-typed status   | Same wire fields; string-union status           |
| `CreateReservationRequest` | Same four request fields              | Same four request fields                        |
| Resource/reservation enums | Separate TypeScript enum declarations | String unions with the same allowed wire values |

The old module additionally declares `User`, for which no active DTO consumer was
found. The field discrepancies conflict with `docs/openapi.yaml` resource and error
schemas at lines 156 and 207. This makes the unused module a source of misleading
context for future edits even though current handlers do not import it.

### Active frontend/backend DTOs: matching, separate boundaries

`src/types/reservation.ts` and `client/src/api/types.ts` both describe `Resource`,
`Reservation`, `ErrorResponse`, and reservation-creation input
(`CreateReservationRequest` / `CreateReservationDTO`). They also repeat resource
and reservation-status string unions. The frontend already reduces local field
duplication through `Reservation extends CreateReservationDTO`.

Backend resource/reservation services import their DTO contracts rather than
redeclaring them. The service-local `HealthStatus` interface is unique and is not
duplicate API-client debt. Persistence interfaces are also distinct: Mongoose
documents contain ObjectIds, Dates, and internal fields, while wire DTOs contain
serialized strings. Do not collapse document and response interfaces.

The browser and backend use separate TypeScript configurations and dependency
boundaries. Directly importing backend modules into the client would undermine
that separation. Any later shared-contract extraction needs a deliberate layout;
the current audit does not introduce a package, generator, or shared runtime.

## Additional low-priority observations

- `openapi.yaml` and `docs/openapi.yaml` are byte-identical copies. The documented
  canonical contract is `docs/openapi.yaml`. Check lab/tool consumers before
  consolidating the duplicate or adding a synchronization check.
- `src/models/Resource.ts` and `src/models/Reservation.ts` are two-line re-export
  modules, not duplicate schema implementations. No current imports of these alias
  paths were found; removal would save little and requires checking consumers.
- The identifier predicate is repeated at `client/src/api/campushubApi.ts:13` and
  `client/src/utils/bookingValidation.ts:18`. The backend's equivalent pattern
  remains necessary at its trust boundary.
- Repeated status/alert markup and two date fields are small. Their labels,
  accessibility relationships, and semantics differ; no generic component is
  justified by the present duplication alone.

## Verification and refactoring safeguards

- TypeScript AST inspection found exactly four controller catches, one browser
  `fetch` call, five component modules, and zero component modules over 150 lines.
- Import searches found no references to the obsolete backend DTO module or the
  two model alias paths. The two OpenAPI files passed a byte comparison.
- Report formatting and `git diff --check` passed. Runtime tests were not rerun
  for this documentation-only audit; existing tests were inspected, not executed.
- A later backend change should run typecheck, build, lint, and the reservation
  integration suite with `MONGODB_TEST_URI` pointing to a test replica set.
- A later frontend change must run its typecheck, build, lint, and API/state tests.
  Existing tests cover wire-field drift, structured errors, timeouts/aborts,
  booking validation, and active-reservation filtering. They do not directly mount
  React hooks/components, so lifecycle changes also need appropriate UI verification.

The proposed work preserves Route -> Controller -> Service -> Model, keeps HTTP
calls in the frontend API layer, retains strict typing and safety checks, and
requires no new dependencies or `.js` source/configuration files.
